# Doctrine

Durable policy extracted from repeated work.

---

## Purpose

Doctrine captures what the team has learned and validated across multiple projects. It is not:

- **Motivational prose.** "Always ship quality code" is not doctrine.
- **Untested principles.** Ideas without evidence belong in speculation, not doctrine.
- **Timeless absolute.** Doctrine should be revisited when context changes.

Doctrine answers: *What have we learned that holds across projects? What guidance is evidence-backed?*

---

## What Makes Doctrine

- Derived from repeated experience or review
- Supported by concrete evidence (reviews, examples, metrics)
- Specific enough to be actionable
- Honest about its limitations and conditions

## Adding Doctrine

Good doctrine requires:

1. Pattern observed across multiple projects
2. Evidence documented (examples, scores, outcomes)
3. Boundaries clarified (when it applies, when it doesn't)
4. Language tested with others

If you're unsure, add it to the planned list rather than documenting prematurely.
